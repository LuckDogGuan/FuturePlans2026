# Phase 5：触发与边界验证

时间：2026-10-19。审查依据：包内SKILL.md、skill-creator的意图/授权/渐进披露/行为验证规则。方法是现实请求的桌面推演，加本地引用与素材存在性核对；没有操作设备，没有运行学习实验。标题数量、模型数量或格式检查不能认证决策质量。

## 行为判断

| 现实请求 | 本包应有行为 | 当前文本判断 |
|---|---|---|
| “按现有板卡细化两周C和寄存器练习” | 读取现状与假期条件，给有边界的小任务及证据，沿用已明确条件 | 能路由到模型1/3，避免纯刷课；但“独立练习与可审阅修改”容易被理解为规划授权也允许直接改代码 |
| “解释位域写入为什么不一定只动一个bit” | 按编译器/ABI/寄存器语义解释，缺型号时保留设备结论未知 | 模型1与官方核查路径适合；不必为一问强制产出整套代码、三图和故障实验 |
| “QEMU成功，能认定真实PCIe链路没问题吗” | 拒绝外推，列已测模型和未测链路/时序 | EDU边界明确，未把模型成功当实板证明 |
| “已有明确部署许可，继续同一台实验板的诊断更新” | 核对动作仍在既有授权内后继续，超出范围才补授权 | 当前“按实际授权范围处理”没有强制重复审批，不能把它误读成每次都要问；可加一句减少调用者误判 |
| “上传超时，没日志没型号，直接说根因” | 区分可能路径，先完成不依赖缺失信息的分析，不能猜一个根因当事实 | 有“保留未知”原则，但未明确根因确认与待验证假设的输出契约 |

纯薪酬承诺、人物履历、RTL设计或通用硬件采购不应因“嵌入式”关键词自动扩进本框架。当前说明偏任务规划，能够支持此边界；不需要把它扩成通用诊断/部署技能。

## 三处最小文本改进建议

以下仅为建议，未改SKILL。

1. 替换授权段为：“仅请求规划时，只生成规划和必要资料核查，不据此修改代码或设备。编写练习、改代码、部署、刷板、采购和发布分别按已有明确授权执行；同一范围已获授权不重复询问，只有新增范围或关键身份不明时补齐条件。”这既防越权，也避免无根据审批阻塞。
2. 在启发式3后补：“把根因分为已确认、待验证假设、仍未知。已确认须给出能支持因果判断的现场/源码或对照证据；证据不足时列剩余假设与下一项最小验证，不能为交付完整结论而猜测。”不要求所有故障都必须复现才允许合理静态判断。
3. 将激活步骤4开头改为：“用户要任务规划或排错实验时，输出以下任务要素；只问概念或审阅结论时，按所需解释与证据回答，不强制新建代码或实验。”保留框架价值，避免固定产物模板扩大简单请求。

结论：框架的技术证据边界基本成立。最值得改的是授权表述和根因状态，第三项改善轻量请求路由；资料清单及索引补齐后，再依据实际行为而非结构计数判断可用性。
